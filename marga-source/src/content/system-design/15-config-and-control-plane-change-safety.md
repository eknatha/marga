Many of the largest recent outages were not hardware failures or attacks. They were a change: a configuration file, a routing update, a policy, a feature list. Changes to data are often pushed faster and wider than code, with fewer checks. Design the change path as carefully as the serving path.

## What you will learn

- Explain why configuration is code with a bigger blast radius
- Validate, stage and canary configuration changes
- Keep a last known good copy and a fast rollback
- Separate the control plane from the data plane

## Config is code

A configuration value can crash a binary, redirect traffic or disable security as surely as a code change. Yet it is often edited by hand, pushed everywhere at once and reviewed less. Give config the same path as code: version control, review, tests, staged rollout, rollback.

## Validate before you push

- **Schema and bounds:** types, ranges, size limits. A file that doubles in size should be rejected before it reaches the proxy.
- **Semantic checks:** does it parse in the real consumer, in a test harness that loads it like production?
- **Diff size:** a change that rewrites half the file is suspicious; require extra review or approval.
- **Compatibility:** old binaries must tolerate new data and new binaries old data; a new field read by a new feature must be safe when blank.

## Stage the rollout

Apply to a small cell or percentage, wait a bake time, check real health signals (error rate, latency, crash count), then proceed. Make the rollout automatic and stoppable. Avoid "global replication in seconds": that is an excellent way to deliver a bad value to everyone before a person can react.

## Last known good and fail static

When a consumer loads a bad config, it should keep running with the previous valid one and raise an alert, not crash. Fail static: keep serving with the last good data. Pair with a fast rollback that does not depend on the broken system.

## Control plane versus data plane

The **data plane** handles user traffic; the **control plane** changes configuration and scale. A good design lets the data plane keep working if the control plane is down or wrong. On 2 November 2023 Cloudflare's control plane and analytics primary site lost power; customers could not change settings, and logs were lost for about two days, yet traffic mostly flowed. The reverse failure is worse: a control plane that pushes a bad value to the data plane everywhere.

## Real cases

- Cloudflare, 18 November 2025: a database permissions change made a query return duplicate rows; the bot-management feature file doubled in size, passed a hard limit in the proxy and crashed it on every machine that loaded it.
- Microsoft Azure Front Door, 29 October 2025: incompatible metadata passed health checks, rolled out globally and triggered a latent bug in the data plane; recovery took about 4.5 hours.
- Google Service Control, 12 June 2025: a policy with blank fields met an unprotected new feature.
- Akamai edge DNS, 22 July 2021: a configuration update triggered a component bug; rolled back after about an hour.
- Facebook, 4 October 2021: a backbone configuration change withdrew routes.

Read each case file for the sourced details.

## Safe-change checklist

1. Can this change be previewed against production traffic or data?
2. What is the smallest first stage and the stop signal?
3. What is the previous good state and how long does rollback take?
4. What happens if the consumer receives garbage?
5. Is the person fixing it dependent on the thing that is broken?

```predict

???
A size and shape check before publishing, staged rollout with a bake time, consumers that keep the last good file when a new one is invalid, and a kill switch. Any one of these would have limited the blast.
> The generator and the consumer both need guards.
```

## How it fails

Validation exists but tests a different parser. Staging exists but the pipeline has a "fast path" used in emergencies. Rollback needs the control plane that is down. The change tool and the monitoring share the same dependency.

## Incident: A file that doubled

> **Incident:** A generated configuration file doubled in size, exceeded a fixed limit in the proxy and the proxy crashed wherever it loaded it.

```console
$ ls -l /etc/proxy/features.json
-rw-r--r-- 1 root root 2411873 features.json
$ journalctl -u proxy -n 2
proxy: feature count 400 exceeds limit 200
proxy: fatal: aborting
```

This console output is a simulated illustration. The real 18 November 2025 Cloudflare incident is in the case file with its sourced timeline and remediation list. A pre-publish size check, a fail-static loader and a global kill switch are the generic design answers.

## Interview question

"How would you make config pushes safe?" Version and review, validate with the real parser, canary by cell, automatic halt on error rate, last known good, and a rollback that works when the control plane is down.

## Common mistakes

- Pushing config to all regions at once
- A fast path that skips staging
- Consumers that crash on bad input
- Rollback depending on the failed system
